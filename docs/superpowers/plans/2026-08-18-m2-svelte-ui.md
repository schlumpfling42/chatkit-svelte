# M2 — Svelte Bindings + Minimal UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Git note:** commit steps are intentionally omitted — the repo owner handles git operations manually. Do not run `git add`/`git commit` while executing this plan unless explicitly asked to in the moment.

**Goal:** Build `@chatkit-svelte/svelte` (the Svelte 5 runes-based `createChatStore`, a `<ChatProvider>` component, and the `getChatContext()` headless primitive) and `@chatkit-svelte/ui` (`<ChatWindow>`, `<MessageList>`, `<Composer>`, and the default CSS token theme) — the minimal end-to-end path from spec §22 M2: a working chat window that streams assistant text and lets the user send messages, styled by tokens, built entirely on `@chatkit-svelte/core` (M0) and testable against `@chatkit-svelte/core`'s `createFixtureTransport` without a real backend.

**Architecture:** `createChatStore` wraps `@chatkit-svelte/core`'s `reduceEvent`/`createPluginHost`/`ChatTransport` in Svelte 5 runes (`$state`), exposing reactive getters (`messages`, `runStatus`) plus `sendMessage`/`abort`/`dispose`. `<ChatProvider>` constructs one store and publishes it via Svelte context; `getChatContext()` is how descendant components read it back. `<ChatWindow>` composes `<MessageList>` (renders `store.messages`, with an optional `message` snippet for full customization per spec §9) and `<Composer>` (a form that calls `store.sendMessage()`). None of this milestone renders markdown, tool calls, or attachments — those are M3's plugins; `MessageList`'s default renderer only understands the `text` content-part type, same restriction M0's reducer already has no opinion beyond.

Every module and every test in this plan has already been written and verified — `svelte-check` clean, `tsc` clean, all tests passing (real `@testing-library/svelte` component rendering + real DOM assertions, no shallow rendering) — in a scratch sandbox. Follow it as written.

**Tech Stack:** Svelte 5 (runes: `$state`, `$props`, `untrack`), `@sveltejs/vite-plugin-svelte`, `vite-plugin-dts`, Vitest with `jsdom` environment, `@testing-library/svelte` + `@testing-library/jest-dom`, `svelte-check` for typechecking `.svelte`/`.svelte.ts` files (plain `tsc` does not understand rune syntax — this is why both new packages need `svelte-check`, already present as a devDependency in both package.json scaffolds).

**A build-tooling decision that deviates from spec §19's generic guidance, made and verified during validation:** spec §19 says every package builds via `vite build --mode lib` + `vite-plugin-dts`. For a *published* Svelte component library, the ecosystem-standard tool is `@sveltejs/package` (`svelte-package`), which ships `.svelte` source mostly uncompiled so the *consumer's* Svelte compiler processes it (better tree-shaking, no double-compilation). It was tried in the scratch sandbox and works — but it copies the entire input directory wholesale with no built-in test-file exclusion, so co-located `*.test.ts` files leak into `dist/` unless test files live in a separate directory outside the packaged input (a bigger structural change than this milestone's scope justifies). Since `chatkit-svelte` is an internal monorepo (workspace-linked packages, not published to a public registry), the "consumer optimizes against raw `.svelte` source" benefit doesn't apply here, and the cost (a second toolchain, restructuring test file placement) isn't worth it. **Decision: `@chatkit-svelte/svelte` and `@chatkit-svelte/ui` use the same `vite build --mode lib` + `vite-plugin-dts` pattern as `@chatkit-svelte/core`/`@chatkit-svelte/transport-agui`**, with `@sveltejs/vite-plugin-svelte` added to compile the `.svelte`/`.svelte.ts` files into the bundle, and `svelte`/`svelte/*` externalized via `rollupOptions.external` so the peer dependency isn't duplicated. This was verified end-to-end in the scratch sandbox: the built bundle correctly imports `svelte`/`svelte/internal/client` as externals rather than inlining them, and — because Vite's lib build only follows what `src/index.ts` actually imports — test files are never pulled into the bundle (no exclusion config needed, unlike `svelte-package`). If a future milestone needs this package published externally, revisit this decision then.

- [ ] **Step 3: Write `packages/svelte/src/chat-store.svelte.ts`**

The file extension is `.svelte.ts`, not `.ts` — this is what tells Svelte's compiler (via `@sveltejs/vite-plugin-svelte`) to process rune syntax (`$state`) in this module. A plain `.ts` file cannot use runes.

```ts
import { reduceEvent, initialState } from '@chatkit-svelte/core';
import { createPluginHost } from '@chatkit-svelte/core';
import type { ChatConfig, ChatEvent, Message, PluginContext, RunAgentInput, UserInput } from '@chatkit-svelte/core';

export function createChatStore(config: ChatConfig) {
  let state = $state(initialState(config.initialState));
  let currentRunId: string | null = null;
  let disposed = false;

  const transport = config.transport;
  const pluginHost = createPluginHost(config.plugins ?? []);

  const ctx: PluginContext = {
    getState: () => state,
    dispatch: (event: ChatEvent) => {
      state = reduceEvent(state, event);
    },
    sendRun: (partial) => startRun(partial),
    logger: {
      debug: () => {},
      warn: () => {},
      error: () => {},
    },
    storage: {
      get: () => undefined,
      set: () => {},
    },
    config,
  };

  pluginHost.init(ctx);

  async function consumeStream(stream: AsyncIterable<ChatEvent>) {
    try {
      for await (const event of stream) {
        if (disposed) return;
        await pluginHost.runHook('onEvent', event, ctx);
        if (disposed) return;
        state = reduceEvent(state, event);
        if (event.type === 'RUN_FINISHED' || event.type === 'RUN_ERROR') {
          currentRunId = null;
        }
      }
    } catch (error) {
      if (disposed) return;
      const chatError = {
        code: 'STREAM_ERROR',
        message: error instanceof Error ? error.message : String(error),
        recoverable: false,
        raw: error,
      };
      state = { ...state, runStatus: 'error', error: chatError };
      await pluginHost.runHook('onError', chatError, ctx);
    }
  }

  async function startRun(partial: Partial<RunAgentInput>) {
    currentRunId = crypto.randomUUID();
    const input: RunAgentInput = {
      threadId: config.threadId ?? 'default',
      runId: currentRunId,
      messages: state.messages,
      tools: config.tools ?? [],
      state: state.sharedState,
      ...partial,
    };
    await transport.sendRun(input);
  }

  async function sendMessage(input: UserInput): Promise<void> {
    const processed = (await pluginHost.runHook('beforeSend', input, ctx)) as UserInput;
    const message: Message = {
      id: crypto.randomUUID(),
      role: 'user',
      parts: [{ type: 'text', text: processed.text }, ...(processed.attachments ?? [])],
      createdAt: Date.now(),
      streaming: false,
    };
    state = { ...state, messages: [...state.messages, message] };
    await startRun({});
  }

  async function abort(): Promise<void> {
    if (currentRunId) await transport.abortRun(currentRunId);
  }

  function dispose(): void {
    disposed = true;
    pluginHost.dispose();
    transport.dispose();
  }

  const stream = transport.connect({ threadId: config.threadId ?? 'default' });
  void consumeStream(stream);

  return {
    get state() {
      return state;
    },
    get messages() {
      return state.messages;
    },
    get runStatus() {
      return state.runStatus;
    },
    registry: pluginHost.registry,
    sendMessage,
    abort,
    dispose,
  };
}

export type ChatStore = ReturnType<typeof createChatStore>;
```

- [ ] **Step 5: Close two lifecycle gaps found by review**

A code-quality review of Step 3's code found two real gaps in `consumeStream`'s fire-and-forget stream consumption, both already folded into the Step 3 code above (the `disposed` flag, the try/catch, the `RUN_FINISHED`/`RUN_ERROR` → `currentRunId = null` clearing): (1) an unhandled rejection if the transport's async iterable throws — no `state.error`, no `runStatus: 'error'`, no `onError` hook fired, so the UI would silently stop updating with no visible cause; (2) `dispose()` didn't stop the background loop, so events already in flight kept getting applied (and plugin `onEvent` hooks kept firing) *after* `pluginHost.dispose()`/`transport.dispose()` already tore things down. A third, minor issue was fixed alongside them: `currentRunId` was never cleared on a finished/errored run, so `abort()` stayed a no-op-defeating "if in flight" check forever after the *first* run — it would call `transport.abortRun()` on an already-finished run.

Add these three tests to `packages/svelte/src/chat-store.test.ts`, inside the existing `describe('createChatStore', ...)` block:

```ts
  it('surfaces a stream error via state.error and runStatus instead of an unhandled rejection', async () => {
    const throwingTransport = {
      connect: async function* () {
        throw new Error('boom');
      },
      sendRun: vi.fn(async () => {}),
      sendFrontendToolResult: vi.fn(async () => {}),
      abortRun: vi.fn(async () => {}),
      dispose: vi.fn(),
    };
    const store = createChatStore({ transport: throwingTransport, threadId: 't1' });

    await vi.waitFor(() => {
      expect(store.runStatus).toBe('error');
    });

    expect(store.state.error).toMatchObject({ code: 'STREAM_ERROR', message: 'boom', recoverable: false });

    store.dispose();
  });

  it('stops applying events once dispose() has been called', async () => {
    const events: ChatEvent[] = [
      { type: 'TEXT_MESSAGE_START', messageId: 'm1', role: 'assistant' },
      { type: 'TEXT_MESSAGE_CONTENT', messageId: 'm1', delta: 'hello' },
    ];
    const transport = createFixtureTransport(events, { delayMs: 20 });
    const store = createChatStore({ transport, threadId: 't1' });

    store.dispose();
    await new Promise((resolve) => setTimeout(resolve, 60));

    expect(store.messages).toHaveLength(0);
  });

  it('clears the in-flight run id once a run finishes, so a later abort() is a no-op', async () => {
    const events: ChatEvent[] = [
      { type: 'RUN_STARTED', runId: 'r1', threadId: 't1' },
      { type: 'RUN_FINISHED', runId: 'r1' },
    ];
    const transport = createFixtureTransport(events);
    const abortSpy = vi.spyOn(transport, 'abortRun');
    const store = createChatStore({ transport, threadId: 't1' });

    await vi.waitFor(() => {
      expect(store.runStatus).toBe('idle');
    });

    await store.abort();

    expect(abortSpy).not.toHaveBeenCalled();

    store.dispose();
  });
```

The first test constructs a minimal object literal satisfying `ChatTransport` directly (not `createFixtureTransport`, which can't be made to throw from `connect()`); `getCapabilities` is optional on the interface so the literal satisfies the type without it.

import { getContext, setContext } from 'svelte';
import type { ChatStore } from './chat-store.svelte';

const CHATKIT_CONTEXT_KEY = Symbol('chatkit');

export function setChatContext(store: ChatStore): void {
  setContext(CHATKIT_CONTEXT_KEY, store);
}

export function getChatContext(): ChatStore {
  const store = getContext<ChatStore | undefined>(CHATKIT_CONTEXT_KEY);
  if (!store) {
    throw new Error('[chatkit] getChatContext() must be called within a <ChatProvider>');
  }
  return store;

- [ ] **Step 2: Write `packages/svelte/src/ChatProvider.svelte`**

```svelte
<script lang="ts">
  import { createChatStore } from './chat-store.svelte';
  import { setChatContext } from './context';
  import type { ChatConfig } from '@chatkit-svelte/core';
  import { untrack, type Snippet } from 'svelte';

  interface Props {
    config: ChatConfig;
    children: Snippet;
  }

  let { config, children }: Props = $props();

  // config bootstraps the store once at mount — it's intentionally not meant
  // to be reactively re-applied if the caller's config object identity
  // changes later, so untrack() here silences Svelte's (accurate, but not
  // applicable to this design) "only captures the initial value" warning.
  const store = untrack(() => createChatStore(config));
  setChatContext(store);
</script>

{@render children()}
```

Without `untrack()`, `svelte-check` reports: `"This reference only captures the initial value of 'config'. Did you mean to reference it inside a closure instead?"` (`state_referenced_locally`). This is accurate — `createChatStore(config)` is called once, non-reactively, by design (the store bootstraps from the config it's given; it's not meant to re-construct itself if the caller passes a new config object on a later render) — `untrack()` is the correct way to tell Svelte that's intentional rather than working around the warning some other way.

### Task 8: Fix real gaps found by a final holistic review

A final review of the whole milestone (after Tasks 1–7 individually passed their own spec/quality reviews) found two **Critical** and two **Important** issues that only became visible when reading the milestone as a whole rather than task-by-task. All four are fixed here, with the fixes folded directly into what Tasks 3/5/6/7 produce — **the code blocks embedded in those earlier tasks are now stale**; this task's code blocks are the authoritative final versions of the files it touches.

**Issue 1 (Critical) — the theme never activates.** `tokens.css` scoped every custom property under `:root[data-chatkit-theme]`, but `:root` only ever matches `<html>`. `ChatWindow.svelte` sets the `data-chatkit-theme` attribute on its own wrapper `<div>`, not `<html>` — so none of the `--ck-*` custom properties were ever defined anywhere in the DOM tree the component actually renders into. Verified empirically: `div.matches(':root[data-chatkit-theme]')` is `false` in jsdom for the wrapper div; the same attribute on `<html>` would match, but nothing in this component library ever touches `<html>`.

**Issue 2 (Critical) — nothing consumed the tokens even if Issue 1 were fixed.** `ChatWindow.svelte`, `MessageList.svelte`, and `Composer.svelte` had zero `<style>` blocks. The `ck-message--user`/`ck-composer__input`/etc. class names were pure unstyled hooks. "Default theme tokens" was a named M2 deliverable that didn't functionally exist — fixed by adding real (deliberately minimal, not a design pass) scoped `<style>` blocks that read the tokens via `var(--ck-*)`.

**Issue 3 (Important) — the build silently destroyed the token file.** Task 7 Step 4's manual `cp packages/ui/src/tokens.css packages/ui/dist/tokens.css` only survives until the *next* build — Vite's lib build empties `dist/` by default, and `tokens.css` isn't imported from any JS/TS file so the bundler never touches it. Since `package.json`'s `exports` map promises `"./tokens.css": "./dist/tokens.css"`, a fresh build (CI, clean clone) shipped a package where that import path resolved to nothing. Fixed with an inline Vite plugin (`closeBundle` hook, pure Node `fs`, no new dependency) that copies the file on every build — this **replaces** Task 7 Step 4's manual `cp` step; don't do that step separately once this task's `vite.config.ts` is in place.

**Issue 3b (found while verifying Issue 2's fix) — the newly-real component styles had nowhere to go.** Adding `<style>` blocks made Vite extract a separate CSS chunk during the build, but `package.json`'s `exports` map had no path for it, so consumers had no way to import it (Node's `exports` field blocks resolution of anything not listed). Fixed by pinning the CSS output to a stable filename (`assetFileNames: 'style.css'`) and adding a `"./style.css"` export.

**Issue 4 (Important) — `<ChatProvider>` leaked the store's transport connection on unmount.** `chat-store.svelte.ts`'s lifecycle hardening (Task 2 Step 5 — stopping in-flight event processing, disposing the plugin host and transport) was real and unit-tested, but unreachable through the only supported usage pattern: `<ChatProvider>` called `createChatStore(config)` but never called `store.dispose()` on unmount. In a real app where a chat panel mounts/unmounts (route change, closing a panel), the transport connection never actually closed. Fixed with `onDestroy(() => store.dispose())`.

## Addendum (added retroactively during M3): a packaging bug rooted in this milestone

M3's final holistic review found that `packages/svelte/vite.config.ts` (Task 1 Step 3, and reaffirmed unchanged in Task 8) and `packages/ui/vite.config.ts` (Task 5 Step 3 / Task 8 Step 5) only ever externalized `svelte`/`svelte/*` in `rollupOptions.external`, never the `@chatkit-svelte/*` workspace packages each one depends on (`@chatkit-svelte/core` for `svelte`; `@chatkit-svelte/core` + `@chatkit-svelte/svelte` for `ui`). That meant `@chatkit-svelte/ui`'s build silently inlined the whole of `@chatkit-svelte/svelte`'s source — including `context.ts`'s module-level `const CHATKIT_CONTEXT_KEY = Symbol('chatkit')` — as a second, distinct copy baked into `ui`'s own `dist/index.js`. Since `Symbol('chatkit') !== Symbol('chatkit')`, any real consumer using `<ChatProvider>` (from `@chatkit-svelte/svelte`) together with `<ChatWindow>`/`getChatContext` (from `@chatkit-svelte/ui`) got a hard `"must be called within a <ChatProvider>"` crash even with correct usage — undetectable by this milestone's own tests because every test here only ever exercised one package's source directly, never two packages' *built* `dist/` artifacts together.

Fixed and fully documented in `docs/superpowers/plans/2026-08-19-m3-plugin-system.md` (Task 6, Step 4) — added the missing `@chatkit-svelte/*` entries to `rollupOptions.external` in six packages' `vite.config.ts` files (including `svelte`/`ui`, whose configs originated here), rebuilt everything, and verified via a revert-reproduce-refix check against real `dist/` output. No source code in this milestone's own files needed to change — this was purely a build-config gap. Left as a pointer here rather than restating the fix, since the authoritative writeup lives in the M3 plan.
